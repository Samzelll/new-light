# СКИЛ: НА АУТСОРС

Цель: экономить лимиты пользователя. Тяжёлую генерацию кода отдаём другому ИИ (Claude Code или GLM), а сам агент готовит точное, чистое ТЗ без лишнего контекста и проверяет результат по строгим критериям приёмки.

---

## 1. Запуск
- **Ручной запуск:** При запросе вида `"на аутсорс: [задача]"` → сразу собрать готовый пакет без лишних рассуждений.
- **Автоматический запуск:** Если задача проходит фильтр из раздела 2, агент сообщает:
  > *«Это лучше отдать на аутсорс»*
  и сразу прикладывает сформированный пакет. Окончательное решение остаётся за пользователем.

---

## 2. Фильтр задач (Правило 3-х «ДА»)
Делегируем задачу на аутсорс **только если все 3 условия выполняются**:
1. **Локальность:** Задача затрагивает 1–2 файла или изолированный модуль/компонент?
2. **Чёткость:** Вход и выход описываются буквально одной фразой?
3. **Автономность проверки:** Результат можно проверить по типам/контракту/логике без запуска всего монолитного проекта?

> **Если хотя бы одно «НЕТ»:** агент выполняет задачу сам в текущем чате и кратко (в 1 предложение) поясняет, почему аутсорс неэффективен.

---

## 3. Выбор исполнителя

| Исполнитель | Когда выбирать | Особенности пакета |
| :--- | :--- | :--- |
| **Claude Code** | Нужен доступ к репозиторию: читает файлы сам, запускает тесты, правит несколько файлов в структуре проекта. | В пакете передавать **только пути к файлам**, контракты и типы, **НЕ** вставляя код файлов целиком. |
| **GLM** | Задача полностью изолирована (чистая функция, утилита, самодостаточный компонент, алгоритм). Репозитория не видит. | Пакет **самодостаточный**: весь необходимый исходный контекст и зависимости внутри. |

> *Если непонятно, какой исполнитель оптимален — задать ровно один уточняющий вопрос.*

---

## 4. Структура пакета (Выдавать одним блоком Markdown для копирования)

```markdown
### TASK PACKAGE FOR [Claude Code / GLM]

**Цель:**
[1 чёткая фраза на английском/русском]

**Контекст:**
- Файлы / Пути: [Для Claude Code: точные пути]
- Типы и сигнатуры: [Интерфейсы, пропсы, DTO]
- Код: [Для GLM: только минимальный необходимый кусок кода]

**Стек и ограничения:**
- Стек: Next.js 15 / React 19 / TypeScript / Tailwind CSS
- Запреты: Не менять сигнатуры существующих функций, не трогать слой mock-сервисов, не использовать inline styles
- Формат экспорта/импорта

**Критерии приёмки:**
1. [Критерий 1]
2. [Критерий 2]
- Пример входа и ожидаемого выхода (или unit-тест / type check)

**Формат ответа:**
- Для GLM: Полный готовый файл/код без лишней болтовни и объяснений.
- Для Claude Code: Правки в репозитории + ровно 3 строки итога (что изменено, что запускал, что не проверено).
```

---

## 5. Протокол приёмки
Когда пользователь возвращается с кодом от внешнего исполнителя:
1. **Проверка по критериям:** Сверить полученный код с критериями приёмки и ограничениями из пакета.
2. **Анализ расхождений:** Найти баги, несоответствия типов, сломанные контракты или пропущенные edge cases.
3. **Вердикт:** Выдать чёткий статус:
   - `ПРИНЯТЬ` (код валиден, готов к интеграции)
   - `ИСПРАВИТЬ` (выдать короткий пакет доработки для внешнего ИИ с описанием конкретной ошибки).
4. **Запрет на переписывание:** Агент **не переписывает код сам**, если пользователь явно об этом не попросил.

---

## 6. Железные правила
1. **Минимум токенов:** Не вставлять в пакет ничего лишнего — каждый лишний фрагмент кода тратит лимиты.
2. **Никаких галлюцинаций:** Не придумывать код, которого пользователь не показывал. Если не хватает контекста — запросить строго нужный фрагмент.
3. **Язык пакета:** Инструкции на языке пользователя, код, технические термины и типы — строго на английском.
